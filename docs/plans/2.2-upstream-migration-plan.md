# Caliptra 2.2 development and upstream publication plan

Prepared November 13, 2026. This is a proposed plan, not authorization to rewrite branches, change PRs, or merge into the release branch.

## 1. Recommended branch model

- **`main-2.1`: release-controlled destination.** Keep 2.2 publication PRs unmerged until the release owner declares the 2.1 freeze complete. Preserve an immutable release tag and an agreed 2.1 maintenance line before the 2.2 cutover.
- **`caliptra-mcu-dev-2.2`: canonical 2.2 integration branch.** Land ongoing 2.2 work here through reviewed PRs. Do not force-rebase this shared branch.
- **Publication branches: derived, reviewable exports.** Refresh the existing foundation stack from canonical development content, then publish the remaining contract, FPGA, and USB units in dependency order. A publication branch is not a second implementation branch.
- **[PR #2273](https://github.com/chipsalliance/caliptra-mcu-sw/pull/2273): tracking umbrella only.** It is already draft. Keep it draft, update its stale description later, and use it to track smaller publication PRs rather than merging the entire development branch.

Do not replace the destination tree with the development tree. Reconcile changes already present on main, then export explicit changes.

## 7. Required-test contract

The active `main-2.1` ruleset currently requires:

- `precheckin`
- `test_emulator (1)` through `test_emulator (8)`
- `test_artifacts`
- `test_spdm`
- One approving review, with linear history; permitted merge methods are squash and rebase.

Several publication heads currently have failed/cancelled checks. Some failures are optional smoke tests, so triage against the actual required list instead of equating every red check with a required failure.

More importantly, retrieved check rollups for #2293/#2295 lack the eight legacy shard names, and #2302 also lacks plain `precheckin`. Dual-revision matrix jobs change check names. Address this explicitly:

1. Prefer stable required gate names backed by the actual dual-revision jobs. Preserve the existing required contexts while enforcing both revisions.
2. Alternatively, coordinate an intentional ruleset migration with repository administrators before relying on renamed contexts.
3. A compatibility gate must fail when an underlying required job fails, is cancelled, or never runs. Do not emit unconditional success or bypass hardware gates to make a PR mergeable.

### Minimum gate for every publication candidate

- All currently required GitHub checks succeed on the final candidate and one reviewer approves.
- Both revision selections use their matching pinned Core and reviewed lockfiles.
- Both full local precheckins pass after reconstruction, along with deterministic register/fuse checks and relevant focused regressions.
- Confirm no unintended 2.1 behavior changes or latest-only USB leakage.
- Preserve released-ROM/runtime compatibility coverage and main's new authorization/SVN requirements.
- After a parent merges, retarget/restack the next PR and rerun checks. Do not rely on green checks from a superseded head or former base.

Current FPGA CI explicitly executes the validated 2.1 bitstream for `test_artifacts` and `test_spdm`; latest is build-only there. Passing those required jobs protects 2.1 but does not establish 2.2 FPGA readiness.

For latest USB acceptance, additionally run nonprivileged emulator tests, explicitly provisioned Linux USB/IP/libusb tests, and the matching-hardware FPGA test where claimed. A skipped privileged test is not a pass. Physical-board tests must be coordinated with the board owner.
